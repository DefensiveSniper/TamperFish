# 多店铺并发聚合与精准发送演进设计稿

- 状态：Draft
- 最近更新时间：2026-03-10
- 适用范围：`/Users/snoopy/Desktop/goofishAggregation`
- 文档用途：作为“多账号 / 商店并发聚合、多 worker 调度、精准发送”方案的唯一持续演进主稿

## 背景与现状

当前项目已经具备单实例闭环能力：

1. 油猴脚本在闲鱼 Web IM 页面采集会话与消息
2. `sync.js` 通过 Chrome CDP 定时读取浏览器本地缓存并补采
3. 本地 API + SQLite 聚合数据，并在 `3210` 提供控制台
4. 待发消息进入 `outgoing_messages` 队列，由浏览器脚本回填发送

当前架构仍然是单店铺、单 Chrome、单 CDP、单同步进程模型，存在以下限制：

- 还不能在同一个控制面里安全聚合多个卖家账号 / 店铺
- 发送链路仍依赖“脚本巡逻到当前会话，再按 `chat_key` 匹配第一条 `pending`”
- `outbox` 事件仍然是“读后处理、处理完再标记”，不适合多个 worker 并发消费
- 如果直接强行多开多个 Chrome 并接入同一个数据库，容易出现会话串线、待发消息串发和 UI 混淆

补充观察：

- 2026-03-10 在当前闲鱼页面结构中，已确认 React props 中可以读到 `sessionInfo.sessionId`
- 左侧会话列表是懒加载虚拟列表，当前可见 DOM 不能代表账号下的完整会话集合

## 目标与非目标

### 目标

- 支持一个控制面稳定管理多个店铺实例
- 每个店铺具备独立 Chrome、独立 profile、独立代理、独立 worker
- 在统一控制台中按店铺隔离并聚合展示会话、消息、待发队列和运行状态
- 将发送主路径升级为“精准定位目标会话后发送”，不再依赖当前巡逻到的会话
- 为后续生产化运行预留重试、幂等、失败隔离和可观测能力

### 非目标

- V1 不引入 Kafka 作为正式消息总线
- V1 不实现中心控制面 + 多主机远程 agent 的分布式部署
- 本轮文档沉淀不直接修改运行时代码、数据库 schema 或 API

## 已确认决策

### 1. 部署与运行拓扑

- V1 采用“单机单控制面 + 多 `shop worker`”形态
- 控制面只启动一次 API / UI / 数据库访问层
- 每个店铺实例独立维护 Chrome、profile、代理、CDP 端口、同步进程、浏览器发送器和健康状态

### 2. 配置组织方式

- 新增统一配置文件 `config/shops.json`
- 每个店铺至少具备：`shopId`、`enabled`、`chromeUserDataDir`、`profileDirectory`、`cdpPort`、`proxy`、`syncIntervalMs`
- 启动器改为读取店铺列表并按店铺拉起对应 worker，而不是当前单实例模式

### 3. 路由与隔离主键

- `shop_id` 是多店铺隔离主键
- `session_id` 是会话精准路由主键
- `chat_key` 继续保留，但降级为展示、兼容与排障字段，不再作为长期唯一发送路由

### 4. 调度与队列方向

- V1 继续使用数据库任务队列，不直接引入 Kafka
- 现有“读取未处理记录，再手动标记 processed”的模型必须升级为具备 `claim / ack / retry / deadletter` 语义的任务队列
- 所有队列读取都必须按 `shop_id` 隔离，避免不同店铺的任务被错误消费

### 5. 精准发送主路径

- 发送主路径固定为“浏览器侧基于 `session_id` 精准定位会话后发送”
- 浏览器 worker 需要在采集阶段同步提取并上报会话定位信息，而不是只上传 `chat_key`
- 左侧会话列表遍历只保留为补水与兜底能力，不再承担正常发送路由职责

### 6. 懒加载场景下的冷启动策略

- 如果目标会话尚未建立可用 locator，本项目默认采用“自动补水后再发”
- 自动补水含义是：浏览器 worker 主动滚动 / 探测 / 重建本地会话索引，命中目标会话后再执行发送
- 如果补水仍失败，任务应进入等待重试状态，而不是回退到当前的全局巡逻匹配逻辑

## 当前假设

- 当前闲鱼页面内部仍能稳定读取到 `sessionInfo.sessionId`、`itemId`、`userId` 等定位信息
- 浏览器侧可以维护一份“`session_id -> locator / sessionInfo`”的内存索引，并在页面刷新后通过补水机制恢复
- 单机部署阶段 SQLite 仍能承载当前预期吞吐，只要补齐原子 claim 和状态迁移语义
- 多店铺实例的 Chrome profile、代理和调试端口都可以做到一店一套、互不复用
- `account_id` 可以在运行时根据实际登录账号识别获得，不要求全部提前静态写入配置

## 核心方案

### 单机单控制面 + 多 shop worker

- 保留一个统一 API / UI / DB 入口
- 每个 `shop worker` 负责本店铺的 Chrome 拉起、watchdog、CDP 同步、浏览器端发送与心跳上报
- 控制面只做聚合展示、任务分发、状态管理和观测，不直接承担店铺级浏览器操作

### 基于 `shop_id + session_id` 的数据隔离

- 所有核心业务表最终都要显式带上 `shop_id`
- 会话与消息的唯一性以 `shop_id + session_id` 为主，而不是仅靠 `chat_key`
- 任何待发消息、事件、失败记录、UI 查询都必须可追溯到所属店铺与所属会话

### 数据库任务队列

- `outbox` 不再只是“是否处理过”的日志表，而是要升级为可调度、可重试、可回执的任务队列
- `outgoing_messages` 也需要具备 claim、失败重试、下一次执行时间、失败原因、死信归档等状态字段
- 多 worker 并发时必须通过原子 claim 保证同一条任务只会被一个执行器领取

### 浏览器侧精准发送

- 浏览器侧采集消息时同时收集 `sessionInfo`
- 发送时按 `session_id` 定位目标会话，而不是依赖“当前刚好巡逻到哪个会话”
- 当前可见 DOM 只是定位缓存的一部分，不能视为完整会话真相
- 若目标会话不在当前渲染窗口中，先补水重建索引，再执行发送

### 自动补水后再发

- 自动补水是懒加载列表下的正式设计，不是临时技巧
- 补水动作的目标是重新发现目标 `session_id` 对应的可操作 locator，而不是盲目遍历第一批可见会话
- 补水应具备次数上限、耗时上限和失败回退状态，避免浏览器端进入长时间无界循环

## 数据模型与接口影响

以下是方案层面已经明确的影响方向，本轮不落代码：

### 数据模型

- `sessions`
  - 预计新增：`shop_id`、`account_id`、`session_id`、`buyer_user_id`、`seller_user_id`、`session_info_json`
- `messages`
  - 预计新增：`shop_id`、`session_id`
- `outbox`
  - 预计新增：`shop_id`、`session_id`、`status`、`claimed_by`、`claimed_at`、`available_at`、`attempts`、`last_error`
- `outgoing_messages`
  - 预计新增：`shop_id`、`account_id`、`session_id`、`session_info_json`、`claimed_by`、`claimed_at`、`next_attempt_at`、`attempts`、`last_error`

### API / 上报接口

- 消息上报请求最终需要带 `shopId`
- 待发消息入队请求最终需要明确 `shopId + sessionId + content + source`
- 浏览器发送执行器最终需要配套的 `claim / ack / fail / heartbeat` 接口
- 旧的只传 `chatKey` 的接口需要保留兼容层，但内部应尽早解析为 `session_id`

### 兼容迁移方向

- 历史只带 `chat_key` 的会话需要兼容读取
- 新采集到的活跃会话要尽快补齐 `session_id` 与 `session_info_json`
- 待绝大多数活跃会话具备精准路由信息后，再切默认发送主路径

## 风险与未决问题

### 已知风险

- 闲鱼 React 内部字段可能变更，`sessionInfo` 的读取方式需要版本敏感监控
- 浏览器重启后 locator 冷启动可能导致短时间内无法立即发送
- 历史数据中缺少 `session_id` 的会话需要兼容迁移，否则会影响发送切换节奏
- SQLite 在更高并发下的锁竞争和 claim 语义需要重点验证

### 未决问题

- `account_id` 的最终命名、采集时机和展示方式是否需要与 `shop_id` 明确区分
- 自动补水的扫描范围、时间预算和失败阈值应该如何量化
- 会话定位信息是否需要额外落本地缓存，还是只保留内存索引 + 后端持久化
- 后续是否需要为远程 agent 提前抽象出协议层，而不是只保留单机预留
